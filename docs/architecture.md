# 系统架构

## 1. 目标

CSGDB 是进程内嵌入式数据库，主要服务终端 AI Agent。系统需要同时处理：

- 小而频繁的状态读写；
- 持续追加的对话、观察和工具事件；
- 结构化事实与关系；
- 文本、向量和时间条件的混合检索；
- 大型 Artifact 的安全保存；
- 断电、崩溃、磁盘空间不足和迁移中断；
- 受限设备上的内存、CPU、I/O 与能耗预算。

## 2. 非目标

首期不实现：

- 分布式共识与多主写入；
- 云数据库服务；
- 裸机 MCU 文件系统；
- 在数据库内运行大模型推理；
- 任意深度、无预算的通用图查询；
- 用自研密码算法替代经过审查的密码学实现。

## 3. 分层

```text
┌─────────────────────────────────────────────┐
│ Agent SDK / Rust API / C ABI                │
├─────────────────────────────────────────────┤
│ CSG-Q Macro / Dynamic AgentPlan             │
├─────────────────────────────────────────────┤
│ Typed IR / Policy / Budget / Optimizer      │
├─────────────────────────────────────────────┤
│ Relational / FTS / Vector / Graph Executors │
├─────────────────────────────────────────────┤
│ Transaction / Connection / Background Jobs │
├─────────────────────────────────────────────┤
│ Storage Kernel / WAL / VFS / Crypto         │
├─────────────────────────────────────────────┤
│ Filesystem / OS Keystore / Hardware Crypto  │
└─────────────────────────────────────────────┘
```

### 3.1 API 层

提供同步 Rust API，并在其上构建运行时无关的异步适配。数据库核心不强制依赖某一个异步运行时。

对移动端和其他语言提供稳定 C ABI。Kotlin、Swift 等绑定由 C ABI 生成，不直接暴露 Rust 内部布局。

### 3.2 Schema 层

`#[derive(Collection)]` 生成：

- 稳定集合和字段标识；
- 指针大小的 `CollectionField<Collection, Value>` 类型化字段句柄；
- 列类型与空值规则；
- 编解码器；
- Schema 指纹；
- 建表、索引和基础 CRUD 语句。

当前实现要求集合 ID、表名、字段 ID、列名、版本和主键全部显式声明。规范描述按字段 ID 排序并在编译期计算 SHA-256 指纹，因此 Rust 类型名、字段名和字段排列不参与持久化身份。宏为每个 Rust 字段生成 `Collection::FIELD_*` 常量，其类型同时携带集合类型和字段值类型，稳定 ID 仍来自显式元数据。索引使用稳定索引 ID、显式物理名称和有序字段 ID 列表，具有独立的 `csgdb-index-v1` 描述和指纹，不改变已有基础 Schema 指纹。首次注册在一个事务中建立或验证物理表与索引，并分别写入 `__csgdb_schema` 和 `__csgdb_index_schema`；已有注册不匹配时返回 `SchemaMismatch`。

`migrate_collection<From, To>` 要求相同集合 ID、严格递增版本、不同指纹和稳定迁移 ID。调用方在同一事务内执行必要的 DDL/数据转换，框架随后验证目标物理 Schema、重建发生变化的派生索引、更新注册表并记录 `__csgdb_migration`。任一步骤出错或 panic 都由事务 Drop 回滚；成功记录可幂等重放。真实子进程测试还会在事务中途直接 `abort`，验证重开恢复。当前是短时独占写事务，影子表、双写和多阶段在线迁移后续跑属于 M6 状态机。

### 3.3 查询层

编译期 Rust DSL 和运行时 AgentPlan 均转换为同一个逻辑 IR。优化器根据统计信息、设备能力和预算生成物理计划。

SQL 只作为可选物理后端语言，不成为公共查询协议。公共 API 不允许 Agent 直接提交任意 SQL。

### 3.4 执行层

执行器由可组合算子组成：

- 结构化扫描和索引查找；
- Join 与聚合；
- 全文召回；
- 向量 Top-K；
- 有界图遍历；
- 时间过滤和衰减；
- 排名融合；
- 投影、解释和流式输出。

每个算子必须报告估算成本，并支持取消和预算中止。

### 3.5 事务与连接

首个内核适配位于 `csgdb-storage`，使用 SQLCipher 提供 B-Tree、事务、WAL、崩溃恢复和页级认证加密。上层只接收经过安全策略验证的 `ResolvedOpenPlan`，底层连接和密钥调用不进入公共 API。

默认采用单写入调度器和多个只读快照：

```text
Writer Producers ──▶ Bounded Queue ──▶ Writer Transaction

Reader 1 ──▶ Snapshot A
Reader 2 ──▶ Snapshot B
Reader N ──▶ Snapshot C
```

设计理由：

- 避免多个写线程反复竞争文件锁；
- 允许写入合并和 Group Commit；
- 使延迟和内存占用更可预测；
- 简化嵌入式设备上的退避与背压。

不允许无限写入队列。队列满时必须返回背压、等待或按调用方策略丢弃低价值遥测事件。

M1 的 `DatabasePool` 已实现这一基础模型：

- 写连接由名为 `csgdb-writer` 的专用线程独占；
- 读连接每次只交给一个 RAII Lease，写连接也只有专用线程访问，因此池内连接使用多线程内核的单所有者模式，避免在调度器之外再次串行化；
- 每连接页缓存取显式 `cache_size_bytes` 与 `memory_budget_bytes / (读连接数 + 1)` 的较小值并向下对齐到 KiB，所有页缓存之和不超过池级内存预算；
- 写队列容量固定，支持等待、立即拒绝和限时等待；
- 同池递归读取和回调内同步提交会返回错误，避免连接或写线程等待自身造成死锁；
- 用户写回调的 panic 被转换为稳定错误，后续任务仍可执行；
- 每个读连接使用文件级只读标志打开，而不只依靠 API 约定；
- 读连接按 RAII 归还，`try_read` 可在池耗尽时立即返回；
- 读事务可以跨并发提交保持同一 WAL 快照；
- 参数化语句列表可以作为一个写任务在单事务中原子提交；
- 相邻的 `execute` 和 `execute_transaction` 任务可以在固定任务数和固定等待窗口内共享一次物理提交；
- 每个逻辑任务由 Savepoint 隔离，约束错误只回滚当前任务；外层提交失败则所有尚待成功响应的任务一起失败；
- 普通写回调、`execute_batch` 和维护操作形成 Group Commit 屏障，保持任意用户事务的边界；
- PASSIVE、FULL、RESTART、TRUNCATE Checkpoint 由写线程串行执行；
- 管理器默认按提交间隔运行 PASSIVE Checkpoint；超过 WAL 未回收帧软上限后，每次写入都重新观测，直到压力解除；
- 自动维护不使用可能等待读者的 FULL、RESTART 或 TRUNCATE 模式；
- 长快照导致的未回收 WAL 帧可由逐次结果和累计统计观测；
- 连接数、实际每连接页缓存、队列长度、活动状态、逻辑任务、物理 Group Commit、维护失败和 WAL 压力可直接观测。

普通单连接 `Database` 同样提供手动 Checkpoint 和引擎本地的自动 Checkpoint 阈值控制。需要最小开销或由宿主自行调度的程序不必启用连接池。管理器自动维护只提供可预测的提交间隔和 WAL 未回收帧软上限，尚未接入快照年龄、设备空闲、电量或热状态；这些信号需要后续设备策略层提供。

## 4. 数据权威性

数据分为两类：

### 4.1 权威数据

- Event；
- State；
- Fact 与版本；
- Memory 正文；
- Edge；
- Artifact 元数据；
- Provenance。

### 4.2 派生数据

- 全文倒排索引；
- 向量索引；
- 图度数与邻接缓存；
- 查询统计；
- 摘要缓存；
- 排名校准参数。

派生数据不得成为唯一副本。恢复时允许丢弃并从权威数据重建。

## 5. 文件组织

默认采用普通 `.db` 主文件。无论数据库是否加密，扩展名保持一致：

```text
example.db
example.db-wal
example.db-shm
```

数据库 UUID、格式版本、索引代数和密钥标识存放在受保护的内部元数据中。WAL 与共享状态文件属于运行时伴生文件，数据库正常关闭或完成 Checkpoint 后可以消失。

Artifact 默认可以作为 Blob 保存在主数据库中。数据规模较大时，可显式启用外部存储：

```text
example.db
example.db.blobs/
└── segment-*.pack
```

外部 Blob Pack 必须使用独立派生密钥加密，并通过主数据库中的事务元数据引用。外部存储是性能和容量选项，不改变主数据库的 `.db` 命名。

## 6. 后台任务

统一后台调度器管理：

- WAL Checkpoint；
- 过期数据回收；
- Artifact Pack 合并；
- 压缩和重新压缩；
- FTS/向量索引构建；
- 迁移；
- 备份；
- 完整性抽检。

任务具有 CPU、I/O、内存、温度和电量预算。前台查询到来时，后台任务必须能够暂停或降低速率。

## 7. 可观测性

核心指标包括：

- 打开与恢复耗时；
- 活跃连接和快照年龄；
- 写队列长度、提交批量和 fsync 延迟；
- WAL 大小与 Checkpoint 进度；
- 缓存命中率；
- 每个查询算子的访问行数、耗时和内存；
- 向量召回数量和重排数量；
- 后台任务进度；
- 数据与索引代数；
- 错误分类和最近一次完整性检查。

默认日志不得包含密钥、明文敏感字段、完整向量或未经处理的用户内容。
