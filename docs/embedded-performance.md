# 嵌入式与性能设计

## 1. 设备假设

首期嵌入式目标接近中端手机：

- ARM64 或 RISC-V 64；
- 2～8 个 CPU 核心；
- 1GB 以上系统内存，但数据库预算通常为 16～128MB；
- 闪存或 eMMC/UFS；
- 支持线程、文件锁、原子重命名和持久化同步；
- 可能存在热降频、电量限制和慢速随机写。

不假设设备持续联网，也不要求设备运行模型推理服务。

## 2. 构建档位

### Full

- 结构化查询；
- 全文检索；
- HNSW 和 Flat 向量检索；
- 图遍历；
- 加密与压缩；
- 备份与修复；
- 完整监控和异步适配。

### Edge

- 1 个写入线程、1～2 个读取线程；
- 有界页缓存；
- Flat 或量化 HNSW；
- 限制后台任务并发；
- 精简分词器；
- 固定查询硬预算；
- 可裁剪高级监控。

### Core

- 事务、Schema、基础 CRUD、状态和事件；
- 不包含 FTS、向量、图统计和大型修复组件；
- 用于空间敏感但仍具备操作系统的设备。

不同档位保持同一权威数据格式。缺少某种索引能力的设备可以忽略对应派生索引，并在能力允许时重建。

当前 `DatabasePool` 默认配置为 2 个只读连接和 64 个等待写任务，分别由 `DEFAULT_READ_CONNECTIONS` 与 `DEFAULT_WRITE_QUEUE_CAPACITY` 表示。Group Commit 默认最多容纳 8 个逻辑任务、等待 250 微秒；管理器默认每 32 次写线程提交运行一次 PASSIVE Checkpoint，并将 4096 个未回收 WAL 帧作为软压力上限。

实现拒绝 0 个读连接、0 容量队列、超过 64 个读连接或超过 65,536 个等待写任务的配置；Group Commit 最大值为 256 个任务和 20 毫秒。嵌入式 Edge 档建议从 1～2 个读连接、16～64 个等待写任务、4～8 个 Group Commit 任务和 100～500 微秒窗口开始，再根据 fsync p95 与前台延迟实测调整。

内存数据库不会自动跨物理连接共享同一内容，因此当前连接管理器明确拒绝 `MEMORY` 打开标志；此场景继续使用单连接 `Database`。

## 3. 设备校准

首次启动或硬件环境显著变化时运行短时校准：

```rust
struct DeviceProfile {
    random_read_iops: u64,
    sequential_write_mib_s: f32,
    fsync_p50_us: u64,
    fsync_p95_us: u64,
    vector_dot_ops_s: u64,
    aes_acceleration: bool,
    simd_width: u16,
    memory_budget: usize,
    thermal_class: ThermalClass,
}
```

校准结果用于选择：

- 页缓存大小；
- 连接数；
- Group Commit 窗口；
- Checkpoint 阈值；
- 向量索引类型；
- 候选集与重排数量；
- 后台任务并发；
- 压缩级别。

设备参数可以由宿主应用覆盖，但数据库需要记录实际生效配置。

## 4. 内存策略

- 基础模式保持较小常驻内存；
- 所有动态查询具有 Heap Budget；
- 向量搜索使用可复用 Scratch Buffer；
- 批量解码使用 Arena，查询结束统一释放；
- 大字段延迟加载；
- 流式返回避免一次性构造完整结果集；
- HNSW 图和文本字典允许按段加载；
- 后台任务不得与前台查询争抢最后的内存余量。

内存不足应返回明确错误并释放临时状态，不能依赖进程 OOM 终止。

## 5. 向量索引

索引选择不能只按数据量决定，还应结合维度、过滤选择性和内存：

| 场景 | 首选 |
| --- | --- |
| 小数据、强过滤 | SIMD Flat |
| 中等数据、低延迟 | HNSW |
| 低内存 | F16/INT8 量化 |
| 高召回要求 | 量化召回 + 原始向量重排 |
| 模型升级期 | 多代索引并存 |

向量索引保存模型标识、维度、距离函数、量化参数和源数据代数。任何不匹配都必须拒绝加载。

## 6. 写入优化

- 单写入调度避免锁抖动；
- 状态更新与遥测事件分优先级队列；
- 仅合并拥有所有权的参数化写入，任意用户回调和维护任务作为屏障；
- Group Commit 同时限制逻辑任务数与收集时间，每个任务使用 Savepoint 隔离；
- 大事务分块，避免 WAL 失控；
- Blob 不进入普通行内 WAL；
- 批量导入使用专用模式，但仍保留崩溃恢复；
- 当前自动维护按提交间隔运行 PASSIVE，并在未回收帧越过软上限后逐次重试；
- 后续 Checkpoint 策略继续接入读快照年龄、设备空闲和电量，FULL/TRUNCATE 只进入明确维护窗口。

## 7. 读取优化

- Prepared Plan Cache；
- 覆盖索引；
- 列延迟解码；
- 零拷贝 Row View，生命周期受 Statement 约束；
- FTS/向量候选先返回 ID，再批量读取正文；
- 对 Agent 常用查询提供显式物化视图；
- 统计信息增量更新，避免频繁全库分析。

## 8. 加密性能

- 优先利用 ARMv8 AES 或其他硬件加速；
- 密钥派生不进入查询热路径；
- 页解密与页缓存协同；
- 加密模式避免将明文映射到普通文件；
- Blob 分块允许按需认证解密；
- 基准必须同时报告加密开启和关闭结果。

不能为了跑分默认关闭认证、同步或临时文件保护。

## 9. 基准维度

每轮性能发布至少覆盖：

- 10K、100K、1M Event；
- 10K、100K、1M Embedding；
- 384、768、1536 维向量；
- 纯结构查询、FTS、向量、图和混合查询；
- 明文与加密；
- 冷启动与热缓存；
- 单次写入与批量写入；
- WAL Checkpoint 干扰；
- 前台查询与后台压缩并发；
- ARM64 真机和 x86_64 参考机。

报告 p50、p95、p99、峰值内存、写放大、数据库大小、能耗和召回质量，不只报告平均吞吐量。

## 10. 当前实测基线

2026-08-01 已在 x86_64 KVM 参考环境建立首轮公共 C 接口基线。固定每连接 4 MiB 页缓存、100K 行和 4 读 1 写后，三轮压力均无错误；CSGDB 明文单连接核心 SQL 操作处于系统 SQLite 的约 ±6% 内，但并发读吞吐为 45.9%。默认加密模式的批量写耗时为 1.36 倍，压力读/写吞吐分别为 25.9%/72.3%，缓存外随机点查、范围查询和更新仍是当前主要瓶颈。

完整环境、方法、分位数、限制和原始数据见 [2026-08-01 运行时性能基线](performance-2026-08-01.md)。这些是实测结果，不是目标值；在 ARM64 真机、冷缓存和更长压力矩阵完成前，不得据此声称已经满足嵌入式发布门槛。

同日完成的首轮底层优化复测中，默认加密路径相对自身基线的随机点查、范围扫描和更新中位耗时分别下降 31.1%、33.0% 和 25.9%，四读一写读取吞吐提升 48.7%，60 秒长压无错误。固定 4 MiB 缓存时仍只达到系统 SQLite 并发读取吞吐的 38.2%，因此性能继续作为发布阻塞项；实现、缓存曲线和原始数据见 [底层性能优化复测](performance-optimization-2026-08-01.md)。
