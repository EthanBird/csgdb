# 2026-08-01 底层性能优化第二轮

## 结论

第二轮把固定 4 MiB 页缓存下的默认加密四读一写吞吐推进到接近系统 SQLite，但尚未通过“所有指标至少超过 SQLite”的硬门槛，性能工作仍是发布阻塞项。

同机、同数据、同 SQL、同缓存、一次预热和三轮交错执行的中位数中，加密压力写吞吐比 SQLite 高 15.0%，读取 p95、p99 分别低 55.3% 和 33.5%，提交 p50 低 56.2%；压力读吞吐仍低 3.5%，随机点查慢 58.4%，范围扫描慢 191.3%，随机更新慢 152.6%。打开、批量建库、文件体积、峰值内存和提交尾延迟也没有全部过线。因此本轮不能标记为性能通过。

相对上一轮 CSGDB 加密中位数，本轮随机点查、范围扫描和更新耗时分别下降 42.1%、48.3% 和 38.8%，四读一写读取吞吐从 3,006,441 提升到 7,664,683（+154.9%），写入吞吐从 151,552 提升到 204,512（+34.9%）。1 KiB 加密页增加了建库页数，批量插入中位数由 249 ms 上升到 340 ms，这项退化被明确保留在报告中。

## 已保留的优化

1. 打包内核关闭跨连接页缓存内存管理和溢出统计，避免独立连接进入同一个全局页缓存互斥组；每个连接继续拥有有界缓存。
2. OpenSSL 3 的 HMAC 与 AES-256-CBC Provider 描述只解析一次。可变 AES 上下文仍逐页创建和释放，密钥与 IV 不跨操作共享。
3. 页 HMAC 使用操作局部的 SHA 状态，绕过逐页 Provider 参数解析和引用计数锁；上下文释放前清零，并以 SHA-1、SHA-256、SHA-512 标准向量和旧格式数据库回读验证字节兼容性。
4. 新建加密数据库使用 1 KiB 页、AES-256-CBC 和完整 HMAC-SHA256 标签。上一版 4 KiB HMAC-SHA256 与旧 HMAC-SHA512 数据库自动探测重开，不隐式改写。
5. 公共 C 连接仍默认 `FULLMUTEX`，池内单所有者连接继续使用轻量互斥模式；认证没有关闭、截断或延迟验证。

直接调用低层 AES、SQLite 共享缓存、线程本地密码上下文复用、512 字节页和关闭内部错误日志均经过实验后被回退：它们分别造成明显性能退化、并发锁错误、收益不稳定、数据库损坏或诊断能力下降。

## 专业剖析结果

参考环境不提供 Linux `perf`，并禁止 `ptrace`，本轮使用 `gprofng` 采样发布构建，并用编译符号和分层基准交叉核对。1 KiB 加密路径中，页 Codec 占 39.1% 包含 CPU，HMAC 占 22.6%，AES 路径占 12.3%，`pread` 占 14.0%；此前的 `EVP_CIPHER_fetch` Provider 锁热点已从调用图消失。

这意味着继续微调 C ABI 或普通分配器不足以关闭剩余差距。下一阶段需要先原型化有生命周期和内存预算约束的“已认证页缓存”，确保缓存键覆盖数据库身份、密钥版本、页号和完整密文，逐出时清零明文；并并行评估版本化 AEAD 页格式，要求防篡改、错误密钥失败、WAL/Checkpoint/恢复矩阵和旧格式迁移全部通过后才允许比较性能。任何缓存命中都不能跳过对未验证密文的认证。
