# ADR 0007：类型化字段句柄作为查询身份边界

- 状态：Accepted
- 日期：2026-08-01

## 背景

Collection 已经同时拥有 Rust 字段名、稳定字段 ID 和物理列名，但查询层不能直接选择其中任意字符串作为字段身份。Rust 字段名适合源码重构，不适合长期落盘；物理列名属于存储实现，若直接进入 AgentPlan 会把 SQL 注入和 Schema 漂移带到公共协议；稳定字段 ID 适合持久化，却不能单独表达 Rust 值类型。

后续 Rust DSL 与动态 AgentPlan 还必须共用同一字段目录。编译期前端需要阻止把一个集合的字段误用于另一个集合，并在比较表达式形成前知道字段值类型；运行时前端则需要把稳定 ID 解析到当前已注册 Schema，而不是信任调用方给出的列名。

## 决策

`#[derive(Collection)]` 为每个 Rust 字段生成 `FIELD_*` 关联常量：

```rust
Memory::FIELD_ID
Memory::FIELD_NAMESPACE
Memory::FIELD_SCORE
```

每个常量的类型为 `CollectionField<Collection, Value>`，例如：

```rust
CollectionField<Memory, String>
CollectionField<Memory, Option<f64>>
```

句柄保存一个指向不可变 `FieldSchema` 的静态指针，并通过泛型参数携带集合类型和字段值类型。它提供稳定字段 ID、物理列、存储类、可空性、主键标记、所属集合和类型安全值编码。普通句柄复制只有一个指针的大小，不执行运行时哈希或注册表查询。

生成常量名来自 Rust 字段名的大写形式，并加 `FIELD_` 前缀。它是源码 API，不是持久化身份；Rust 字段重命名会改变常量名，但只要显式字段 ID 和 Schema 约束不变，数据库指纹不变。宏必须拒绝大小写归一后发生常量名碰撞的字段组合。

持久化查询计划只序列化集合 ID 与字段 ID。执行前根据已注册 Collection Schema 解析到物理列，并重新检查类型、权限和能力。物理列名不接受 Agent 或网络输入。

当前切片只提供身份与类型边界。后续 `Predicate`、`Order`、`Projection` 和查询宏以 `CollectionField` 为入口；字段句柄本身不拼接 SQL，也不直接执行查询。

## 被拒绝的方案

### 在查询宏中直接解析 Rust 字段访问

过程宏可以识别 `m.text`，但函数式构建器、动态 AgentPlan、编辑器补全和宏外复用仍缺少共同的字段对象。

### 使用物理列名字符串

最简单，但会泄漏存储细节、绕过字段权限和类型检查，并使列重命名直接破坏序列化计划。

### 只使用稳定字段 ID 字符串

适合动态协议，不足以让 Rust 编译器检查集合和值类型；每次构造还需要运行时目录查找。

### 为每个字段生成独立零尺寸类型

可以做到零尺寸和更强的类型级身份，但会显著放大宏产物、公共类型数量和错误信息复杂度。一个静态指针大小的统一句柄更适合作为首版边界。

### 将 Rust 字段名作为稳定身份

会让普通重命名改变磁盘与查询计划兼容性，违反既有 Collection Schema 决策。

## 正确性与安全影响

- Rust 编译器可以区分不同集合和不同字段值类型；
- 动态计划只持有稳定 ID，不能借列名绕过 Schema 或权限解析；
- `same_storage_field` 可以验证两个重构前后 Rust 类型是否指向同一持久化字段；
- 句柄编码复用 `FieldValue` 的溢出、空值和存储类检查；
- 句柄不是授权能力，敏感字段仍需在查询验证阶段检查 Capability。

## 性能与兼容性影响

字段元数据由 derive 在编译期生成，句柄复制等同于复制一个静态指针。普通 CRUD 不增加分配、哈希或注册表访问。未来逻辑 IR 可以保存紧凑的目录索引，但该优化不得改变稳定集合/字段 ID 协议。

增加生成的关联常量属于 Rust 源码接口扩展。第一个稳定版本前仍可调整命名；稳定后字段常量改名按源码兼容性规则处理，而持久化格式继续只认显式 ID。

## 回滚方式

移除字段句柄和查询 IR 不影响现有表、索引、Schema 注册、迁移历史、SQL API 或 C ABI。调用方仍可使用 `Collection::schema().fields()` 读取运行时元数据。
