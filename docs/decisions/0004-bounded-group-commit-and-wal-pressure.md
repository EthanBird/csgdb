# ADR 0004：有界 Group Commit 与 WAL 压力维护

- Status: Accepted
- Date: 2026-07-31

## Context

单写线程已经消除连接间写锁竞争，但每个小型参数化任务仍独立提交，设备上的 `fsync` 成本会直接放大尾延迟和写放大。简单地把任意写回调放进同一事务会破坏调用方定义的事务边界；把所有相邻任务视为同一失败域，则会让一个低价值遥测错误回滚无关状态写入。

WAL 维护同样需要明确边界。只依靠固定的内核帧阈值不能暴露长快照造成的回收停滞，而自动运行 FULL、RESTART 或 TRUNCATE 又可能阻塞前台读取。管理器需要可预测、可观测且不会强制终止读快照的策略。

## Decision

1. 只有 `DatabasePool::execute` 和 `execute_transaction` 产生可合并任务，因为它们完整拥有 SQL 与参数。
2. 普通写回调、`execute_batch`、手动 Checkpoint 和配置变更都是严格的队列屏障。
3. Group Commit 同时受最大逻辑任务数和最大收集时间限制；默认值为 8 个任务和 250 微秒，硬上限为 256 个任务和 20 毫秒。
4. 队列保持 FIFO。遇到屏障时立即结束当前收集，不跨越屏障寻找后续任务。
5. 每个逻辑任务在外层事务中使用独立 Savepoint。
6. 语句准备、绑定或执行失败时，只回滚当前 Savepoint；同组其他任务继续执行。
7. Savepoint 管理或外层提交失败属于物理事务错误，所有原本成功的任务都收到错误。
8. 逻辑任务的背压、提交、完成和拒绝计数保持不变；另行统计物理事务数、实际合并任务数和最大批次。
9. 管理器自动维护默认启用，每 32 次写线程提交运行一次 PASSIVE Checkpoint。
10. 4096 个未回收 WAL 帧作为默认软压力上限。越过上限后，每次写入都重试 PASSIVE，直至压力解除。
11. 自动维护不运行 FULL、RESTART 或 TRUNCATE；这些模式只由调用方在明确维护窗口触发。
12. `set_wal_autocheckpoint` 切换到引擎本地策略并关闭管理器策略；`set_automatic_wal_maintenance` 可以重新启用或替换管理器策略。

## Consequences

- 多个小写入可以共享一次持久化提交，同时保持独立错误响应。
- Group Commit 最多增加配置窗口规定的排队延迟，不会无限等待凑满批次。
- 任意用户写回调仍获得独占、完整的数据库语义，不会被外层隐式事务包裹。
- 长读快照继续有效；它造成的 WAL 压力通过统计显式暴露，而不是通过强制 Checkpoint 消除。
- PASSIVE Checkpoint 可以控制可回收帧，但软上限不是严格文件大小上限；持续长快照仍可能让 WAL 增长。
- 后续设备策略可以基于 fsync 延迟、快照年龄、电量和热状态调整参数，但不能突破本决策的有界等待和失败隔离原则。
