# ADR 0003：可控 WAL 维护与参数化批量事务

- Status: Accepted
- Date: 2026-07-30

## Context

有界连接管理器已经将写入集中到单线程，但调用方仍缺少两个关键控制面：

1. 多条带参数语句需要通过回调手工创建事务，容易遗漏回滚和所有权约束；
2. WAL 只能依赖内核默认的自动阈值，无法观察长读快照造成的回收停滞，也无法在应用维护窗口主动截断。

嵌入式设备需要限制 WAL 增长，同时不能用强制 Checkpoint 阻塞前台读写。公共接口必须保留内核输出的 WAL 总帧数和已 Checkpoint 帧数，不能只返回成功或失败。

## Decision

1. `BatchStatement` 拥有 SQL 字符串和参数值，适合跨线程写队列。
2. `DatabasePool::execute_transaction` 将一个语句列表作为单个队列任务执行，并在一个事务中按输入顺序提交。
3. 任一语句的准备、绑定、执行或提交失败都会使整个批次回滚。
4. 显式批量事务不自动合并不同调用方任务，因此不称为 Group Commit。
5. Rust API 提供 PASSIVE、FULL、RESTART、TRUNCATE 四种 Checkpoint 模式。
6. `CheckpointResult` 保留 WAL 帧数、已复制帧数、剩余帧数、锁竞争状态和完整性判断。
7. 数据库名可以指定；缺省的便捷接口只操作 `main`，避免无意维护所有附加库。
8. Checkpoint 和自动阈值修改通过池的单写线程串行执行。
9. 自动 Checkpoint 阈值为连接本地配置，零表示禁用，并拒绝超出有符号 32 位范围的值。
10. C ABI 提供相同的模式、帧计数和阈值控制；不可用帧数使用 `-1`。
11. 池统计累计成功运行的 Checkpoint 和未完整回收的次数。

## Consequences

- 调用方可以低成本提交原子参数化批次，不需要在队列回调中重复事务模板。
- PASSIVE 模式可以用于前台观测，不等待读写锁；RESTART 和 TRUNCATE 应只在合适的维护窗口使用。
- 长读快照不会被强制终止；它造成的剩余 WAL 帧会成为显式结果。
- 当前接口只提供机制，不根据 WAL 大小、快照年龄、电量或前台负载自动选择模式。
- 后续 Group Commit 必须保持每个调用方的结果隔离、背压语义和事务失败边界。
